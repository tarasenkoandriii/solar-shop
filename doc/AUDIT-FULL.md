## 1. Конвеєр карти потенціалу — головний фокус цього аудиту

**Було** (зафіксовано чесно в `AUDIT-PHASE-4.md`): клієнту віддавались сирі
розріджені точки PVGIS без жодної інтерполяції — `leaflet.heat` малював
градієнт "на око" між рідкісними точками, що давало візуально "плямистий"
результат, далекий від "непрерывного растра", як того вимагає ТЗ п.34.2.

**Стало**: реалізована справжня IDW (Inverse Distance Weighting)
інтерполяція — `apps/api/src/solar-map/idw-interpolation.ts`:
- Haversine-відстань між точками (коректна геосферична відстань, не
  євклідова апроксимація в градусах)
- Стандартна формула IDW: `value = Σ(vᵢ / distanceᵢ²) / Σ(1 / distanceᵢ²)`
- Будує щільну цільову сітку (типово 60×60 клітинок) по розрідженим
  вихідним точкам PVGIS
- Результат кешується в новій таблиці `SolarMapInterpolatedGrid` (одна
  строка на резолюцію — climatology майже не змінюється, той самий
  принцип кешування, що й у `SolarYieldEstimate`)
- Адмінка отримала окрему кнопку «Тільки інтерполяція» — можна оновити
  щільність сітки без повторних дорогих викликів PVGIS API
- Клієнтський рендер (`leaflet.heat`) підлаштований під щільні дані
  (радіус зменшено з 35 до 18px — раніше був підібраний під рідкісні точки)

**Що досі свідомо не реалізовано** (і чому): справжній PMTiles-конвеєр
(растеризація → тайли у форматі PMTiles) вимагає або GDAL-класу
інструментів, або растрового рендерингу через `canvas`/`sharp` з нативними
біндингами. Обидва варіанти ризиковані для serverless-деплою на Vercel
Hobby (нативні залежності часто ламаються без спеціальних build-кроків, і
це неможливо перевірити в середовищі без мережевого доступу для
встановлення/збірки). **Свідомий компроміс**: віддаємо клієнту щільний
JSON-масив інтерпольованих точок замість файлу растрових тайлів —
функціонально це та сама теплова карта з градієнтом (вимога ТЗ "не
анімація частинками" дотримана), просто без окремого шару тайлового
сервера. Для 60×60=3600 точок JSON важить ~150-200 КБ — прийнятно для
завантаження на клієнті, не потребує тайлування за розміром даних.

**Якщо знадобиться довести до букви ТЗ**: рекомендація з
`AUDIT-PHASE-4.md` лишається чинною — окремий offline-скрипт (Python,
поза NestJS API) з `scipy`/`pykrige` для інтерполяції та `tippecanoe` для
генерації PMTiles, що виконується вручну раз на рік-два, а не частина
serverless-бекенду.

**Доповнення після повторного проходу (17.08.2026, за окремим запитом)**:
формат точок змінено з масиву об'єктів `[{lat, lng, annualKwhPerKwp}, ...]`
на компактні кортежі `[lat, lng, annualKwhPerKwp]` — на 3600 точках
об'єктний формат означає буквальне повторення ключів "lat"/"lng"/
"annualKwhPerKwp" тисячі разів у JSON, реальні зайві байти на зберіганні
(`SolarMapInterpolatedGrid.cellsJson`), у відповіді публічного API
(дергається на кожному завантаженні `/solar-map`) і у файлі експорту (див.
розділ 6). Це не було виправлено з першого разу — під час написання коду
за замовчуванням обрав об'єктний формат заради читабельності, не
порахувавши реальну вартість повторення ключів на масштабі в тисячі
записів. Виправлено в `idw-interpolation.ts`
(`toCompact()`/`fromCompact()`), фронтенд (`SolarPotentialMap.tsx`)
оновлено — до речі, `leaflet.heat` і так очікує кортежі `[lat, lng,
intensity]`, тож новий формат навіть спростив код на клієнті (менше
перетворень).

## 2. Знайдено й виправлено при повному аудиті

### 2.1 XSS через JSON-LD (сторінка товару)

`dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}` у
`app/[locale]/products/[slug]/page.tsx` — класична вразливість
"JSON-in-script-tag": якщо будь-який рядок усередині об'єкта (напр. назва
товару) містить буквально `</script>`, браузер закриє тег скрипта
передчасно, і залишок рядка відрендериться як довільний HTML. Джерело
рядків — каталог (адмін або Grok-згенеровані описи, ТЗ п.26.3), не прямий
призначений для цього користувацький ввід, але жоден із каналів не
гарантує відсутність цієї послідовності в тексті.

**Виправлення**: `apps/web/src/lib/safe-json-ld.ts` — екранування
`<`/`>`/`&` перед вставкою в `<script>`.

### 2.2 Mass-assignment у `FinancingController.update()`

Ендпоінт приймав `Record<string, unknown>` і передавав весь об'єкт
напряму в `Prisma.financingProgram.update({ data: dto })` — можна було
передати довільні поля, включно з не призначеними для ручного редагування
(напр. `status`, `lastSeenInParserAt`, `needsRecheck` — поля, керовані
парсером, не адміном напряму через цю форму).

**Виправлення**: `UpdateFinancingProgramDto` з explicit білим списком
полів (`name`/`eligibility`/`description`/`url`/`minLoanUsd`/`maxLoanUsd`).

### 2.3 Системна прогалина: global `ValidationPipe` мовчки пропускає inline-типи

**Найважливіша знахідка цього аудиту.** Глобальний `ValidationPipe` в
`main.ts` налаштований з `forbidNonWhitelisted: true` — це мало б
відхиляти запити з зайвими полями. Але NestJS перевіряє це **тільки**,
якщо параметр `@Body()` типізований справжнім класом (з
`class-validator`-декораторами) — для plain TS-інтерфейсів/inline-об'єктних
типів (`@Body() body: { foo: string }`) рантайм-метадані стираються при
компіляції, і `ValidationPipe.toValidate()` **повністю пропускає
валідацію** (перевіряє тільки метатип, а TS-інтерфейс на рантаймі
виглядає як звичайний `Object` — один з типів, явно виключених із
валідації в самому NestJS).

**Практичний наслідок**: усі такі ендпоінти приймали й обробляли **будь-
які** поля без перевірки типів/діапазонів/enum-значень — `forbidNonWhitelisted`
для них не працював зовсім, попри те що в `main.ts` він увімкнений
глобально.

**Знайдено й виправлено 10 екземплярів** (усі — контролери Фаз 3-4, де
писався код найшвидше під час великого обсягу роботи):
- `CalculatorSettingsController` — 3 ендпоінти (`upsertTariff`,
  `applyPowerRangeThreshold`, `applyScalingThreshold`)
- `BusinessPlanController` — 2 ендпоінти (`createManual`, `generateViaAi`)
- `SchemaTemplatesController` — 1 ендпоінт (`update`)
- `SolarMapController` — 3 ендпоінти (`logEmbedView`, `recomputeGrid`,
  `recomputeInterpolation`)
- `CalculatorController` — 1 ендпоінт (`requestDocuments`)

Для кожного заведено справжній DTO-клас із `class-validator`-декораторами
(`@IsIn`/`@IsNumber`/`@IsString`/`@Min`/`@Max` тощо) — тепер
`forbidNonWhitelisted` і валідація типів/enum реально працюють.

**Чому не критично, але важливо виправити**: 9 із 10 знайдених ендпоінтів
уже стояли за `@Roles(UserRole.ADMIN)` — експлуатація вимагала б
скомпрометованого адмін-акаунту, що суттєво знижує реальний ризик
порівняно з публічним ендпоінтом. Але (а) це порушувало явну наскрізну
вимогу ТЗ п.28.7/п.11 ("перевірка DTO/class-validator на нові enum'и —
частина критеріїв готовності кожної фази"), і (б) без валідації типів
неправильні дані (напр. рядок замість числа) просто йшли б у Prisma й
падали з незрозумілою помилкою на рівні БД замість зрозумілого 400
Bad Request. Заодно додав rate limit на єдиний публічний ендпоінт з цього
списку (`POST /solar-map/embed-view`, раніше не мав захисту від накрутки
лічильника показів).

**Перевірено систематично**: `grep` по всьому `apps/api/src` на патерн
`@Body() body: {`/`@Body() dto: {`/`Record<string, unknown>` — після
виправлень **0 залишкових екземплярів**. 20 із 21 DTO-файлу в проекті
використовують `class-validator` (той, що не використовує — простий
ре-експорт `UpdateProductDto` з `create-product.dto.ts`, де валідація вже
є).

## 6. Аудит нової фічі: експорт/імпорт даних карти (міграція між оточеннями)

За окремим запитом, одразу після реалізації.

### Що зроблено

`SolarMapService.exportData()`/`importData()` — той самий паттерн, що
`VendorDataTransferService` (Фаза 2): експорт усіх сирих точок PVGIS
(`SolarYieldEstimate`) + закешованих інтерпольованих сіток
(`SolarMapInterpolatedGrid`) в один JSON-файл, ідемпотентний імпорт через
`GET /admin/solar-map/export` / `POST /admin/solar-map/import`, UI в
адмінці (`/solar-map-admin`) поруч із кнопками перерахунку.

**Навіщо**: точки PVGIS дорого пересчитувати заново — потрібен мережевий
доступ до `re.jrc.ec.europa.eu`, якого в багатьох dev/CI-оточеннях просто
немає (та сама причина, чому ця фіча вже існувала для даних парсера).
Порахував один раз там, де мережа є, — переніс файлом туди, де немає.

**Ідемпотентність**: сирі точки матчаться по унікальному
`(lat, lng, tiltDegrees, azimuthDegrees)` — тому самому ключу, що вже
використовує `PvgisService` для кешування, повторний імпорт того самого
файлу тільки оновлює `annualKwhPerKwp`/`fetchedAt`, не плодить дублі.
Інтерпольовані сітки матчяться по унікальному `resolution`.

**Формат файлу — компактний із самого початку** (враховуючи саме
зауваження, що призвело до цього аудиту): `interpolatedGrids[].cells` —
масив кортежів `[lat, lng, value]`, не об'єктів. `rawPoints`, на відміну
від сіток, лишені об'єктним масивом
(`{lat, lng, tiltDegrees, azimuthDegrees, annualKwhPerKwp}`) — свідомо, не
недогляд: сирих точок на порядок менше (сотні, не тисячі — навіть при
кроці сітки 1° це ~162 точки), і в них 5 полів проти 3 у інтерпольованих
клітинок, тобто виграш від компактного формату тут менший, а читабельність
файлу під час ручної інспекції/дебагу важливіша.

### Знайдено при аудиті — виправлено одразу

**Валідація payload через `unknown`, не inline-об'єктний тип** — на
відміну від помилки, знайденої в розділі 2.3 (де inline-об'єктні типи
`@Body()` мовчки обходили `ValidationPipe`), тут свідомо
використаний `@Body() payload: unknown` — TypeScript `unknown` коректно
проходить через `ValidationPipe` (не намагається валідувати структуру,
але й не видає хибне відчуття захищеності), а реальна валідація формату
(`formatVersion`, наявність масивів) робиться вручну всередині
`SolarMapService.validateImportPayload()` — той самий підхід, що вже
застосований у `VendorDataTransferService.importVendorData()` з Фази 2.
Це узгоджений, а не забутий випадок — на відміну від 10 знахідок у
розділі 2.3, тут із самого початку немає inline-об'єктного типу.

### Свідомі обмеження

- **Немає перевірки розміру файлу перед парсингом** — `JSON.parse(text)`
  на клієнті без обмеження розміру завантажуваного файлу. Для реального
  обсягу даних (максимум кілька сіток по кілька тисяч точок кожна) це не
  проблема на практиці (файл — сотні КБ - одиниці МБ), але немає явного
  захисту від випадкового завантаження величезного/невалідного файлу, що
  міг би підвісити вкладку браузера на `JSON.parse()`.
- **Ендпоінт експорту не rate-limited** — на відміну від імпорту (POST,
  змінює дані), `GET /admin/solar-map/export` не має `RateLimitGuard`.
  Прийнятно — тільки читання, під ADMIN-роллю, не викликає жодних
  зовнішніх API (на відміну від, напр., `recompute-grid`, де ліміт
  захищає від випадкового зловживання дорогими викликами PVGIS) — свідомо
  не обмежений, не недогляд.
- **Немає перевірки, що імпортовані координати належать Україні** —
  можна імпортувати точки з будь-якими lat/lng, включно з тими, що поза
  `UKRAINE_BOUNDS`. Не критично (адмінська фіча, довільні координати не
  зашкодять — просто не потраплять у видиму область карти при рендері),
  але вартий згадки для повноти.

### Чому інші JSON-поля проекту НЕ переведені на компактний формат

Перевірено решту великих JSON-полів у схемі (`ProjectEstimate.
recommendedSpec`, `.conversationLog`, `SchemaTemplate.svgTemplate`) —
жодне з них не має того самого масштабу, що виправдовував би компактний
формат: `recommendedSpec` — типово 3 позиції (панелі/АКБ/контролер), не
тисячі, `conversationLog` — кілька записів діалогу на проєкт. Виграш від
переходу на кортежі там був би непомітний, а втрата читабельності коду
(доступ по індексу `item[2]` замість `item.priceUsd`) — реальна. Компактний
формат застосований там, де дійсно є обсяг (карта потенціалу — тисячі
точок), не механічно скрізь, де є масив JSON.

## 8. КРИТИЧНО: реальна Docker-збірка падала — сліпа зона методу перевірки в цій сесії (18.08.2026)

Andrii повідомив про реальний фейл `docker build` на кроці
`RUN npm run build --workspace=apps/api` (exit code 1). Це виявило
структурну проблему в тому, ЯК проводились усі попередні аудити цієї
сесії — не в самому коді спочатку.

### Корінна причина сліпої зони

Пісочниця, де писався весь код, не має мережевого доступу до
`binaries.prisma.sh` — `prisma generate` там ніколи не міг завершитись
повністю (підтверджено знову в цій сесії: `403 Forbidden` навіть з
`PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1` і навіть з `--no-engine`).
Через це `@prisma/client` у пісочниці — порожня заглушка, і **кожен**
виклик `tsc --noEmit` видавав десятки помилок типу "Cannot find module
'@prisma/client'"/"Prisma has no exported member X" — не пов'язаних із
реальними багами, а виключно з відсутністю згенерованого клієнта.

Щоб не тонути в цьому шумі, з першої фази проекту використовувався
`grep -v` фільтр, що відкидав рядки з певними ключовими фразами
("Cannot find module '@prisma/client'", "has no exported member" тощо).
**Це працювало для свого прямого призначення**, але мало побічний ефект:
**будь-яка РЕАЛЬНА помилка типів, повідомлення якої випадково не
збігалося з жодним патерном фільтра, проходила непоміченою** — а
реальний `docker build` (де Prisma Client генерується по-справжньому,
бо там є мережа) ловить усі помилки без винятку.

### Два реальні багі, знайдені тільки зараз (ручною звіркою схеми з кодом)

1. **`ProjectEstimate.contactChannel`/`.contactValue` — код писав/читав
   поля, яких не було в схемі.** Ці поля прибрали з `ProjectEstimate`
   під час аудиту фічі відправки матеріалів (`AUDIT-PHASE-3-DELIVERY.md`,
   винесли в окрему `ProjectEstimateDelivery` для множинних спроб
   відправки). Але ПІЗНІШЕ, при реалізації чек-листа документів
   (`CalculatorService.requestDocuments()`, Фаза 4), знадобилось поле
   "куди відправити фінальний згенерований пакет" — і замість того, щоб
   свідомо повернути ці два поля в схему, код почав писати їх напряму,
   а схема лишилась незмінною. `business-plan-generation.service.ts`
   так само читав ці неіснуючі поля при відправці готового бізнес-плану.
   **Виправлення**: повернуто `contactChannel String?`/
   `contactValue String?` в `ProjectEstimate` з explicit коментарем про
   те, чим це відрізняється від `ProjectEstimateDelivery` (один цільовий
   контакт на чек-лист, не історія спроб).
2. **`orderBy: [{ goalTags: 'asc' }, ...]` в `BusinessPlanManifestService.
   findAll()` — Prisma не підтримує `orderBy` по scalar list полю
   (`String[]`) стандартним клієнтом.** `goalTags` не є валідним ключем у
   згенерованому `BusinessPlanManifestOrderByWithRelationInput` —
   реальна помилка типів. **Виправлення**: прибрано `goalTags` з
   `orderBy` (сортування там і так не впливало на UI — угруповання по
   тегах відбувається на клієнті, в адмінці, через `Map`).

## 9. Реальний `docker build` (Andrii, 18.08.2026) — ще 3 помилки типів, усі виправлені

Прогноз із розділу 8 підтвердився буквально одразу: перший же реальний
`docker-compose up -d --build` з повністю згенерованим Prisma Client
знайшов **3 нові помилки типів**, яких пісочниця фізично не могла
побачити. Усі — той самий клас проблеми: **nullable поле, що бере участь
у складеному/одиничному унікальному ключі, використане в `where:` для
`findUnique`/`upsert` зі значенням `null`** — Prisma забороняє це на
рівні типів (SQL: NULL не ідентифікує рядок однозначно в контексті
unique-lookup, навіть якщо сам стовпець nullable).

1. **`CartItem.listingId` (nullable) у складеному ключі
   `cartId_productId_listingId`** — `mergeGuestCartIntoUser()` міг
   отримати `item.listingId: string | null` з уже існуючого запису й
   спробувати використати `null` у lookup. Виправлення: явне розділення
   на два шляхи — є `listingId` → звичайний upsert по складеному ключу;
   немає → ручний `findFirst`+`update`/`create` без покладання на
   unique-lookup.
2. **`PromoSettings.category` (nullable) в `product-pricing.service.ts`**
   — `findUnique({ where: { category: null } })` для глобального
   (без-категорійного) override. Виправлення: `findFirst` замість
   `findUnique` (той самий смисл, findFirst не має цього обмеження типів).
3. **Те саме поле в `promo.service.ts`, але в `upsert`** — `findFirst` тут
   не підходить (upsert вимагає validного `WhereUniqueInput`), тому ручна
   find-or-create логіка: `findFirst` → `update`/`create` для
   `category: null`, звичайний `upsert` лишився для конкретних категорій.

**Систематична перевірка після виправлень**: пройдено скриптом усі
`@@unique`/`@id` в схемі на предмет nullable-полів, що беруть у них
участь — знайдено 3 моделі (`Product.manufacturerId_manufacturerSku`,
`PromoSettings.category`, `CartItem.listingId`), перша з них ніде не
використовується як складений ключ у коді (безпечно), решта дві —
виправлені вище. Додатково прогнано `grep` по всьому `apps/api/src` на
`null` всередині `where:` для `findUnique`/`upsert`/`delete` — інших
екземплярів не знайдено.
