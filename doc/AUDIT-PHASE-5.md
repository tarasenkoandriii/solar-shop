додано між розділом 49 (останній зааудований) і розділом 99

## Що перевірено

- `npx tsc --noEmit` для `apps/api` — **0 реальних помилок** на
  кожному кроці (усі залишкові помилки — той самий відомий артефакт
  відсутнього `prisma generate` у пісочниці, підтверджений десятки
  разів на різних файлах, включно з давно робочими)
- Реальний `nest build` (webpack) — `dist/main.js` генерується
  успішно на кожному кроці, попри type-помилки пісочниці
- `npm run build` для `apps/web`/`apps/admin` — проходить чисто на
  кожному кроці, включно з усіма новими сторінками/компонентами
- Численні прямі тести (`node -e`) для конкретної бізнес-логіки:
  формула ΔU для перерізу кабелю, парсинг RSS-enclosure (7
  сценаріїв), евристика дублікатів фінансових програм (реальні дані
  зі скріншотів), ескалація на headless-браузер (4 сценарії статусів),
  валідація імпорту JSON (4 сценарії), перерахунок `Article.status`
  (4 сценарії), пагінація балансу Grok AI (3 сценарії) — систематична
  практика цієї фази: не покладатись на "код виглядає правильним",
  перевіряти напряму, де є можливість

## Найважливіший системний урок цієї фази — один клас багів словився ЧОТИРИ РАЗИ

"Cron-конверт" баг (`CronService.execute()` повертає `{summary,
debugLog, itemsProcessed, itemsFailed, status}`, а конкретні числові
поля результату джоба лежать УСЕРЕДИНІ `debugLog`) — фронтенд-типи
раз у раз описували відповідь як ПЛАСКИЙ об'єкт, звертання до полів
тихо повертало `undefined`, не помилку компіляції:

1. Розділ 72 — `article_parser`/`article_batch_poll` в адмінці
   ("статистика не пише цифри")
2. Розділ 76 — `financing_program_parser` ("Cannot read properties of
   undefined (reading 'length')"), і **того самого разу** знайдено й
   виправлено `solar-map-admin/page.tsx` ДО скарги користувача —
   систематична перевірка після другого прояву
3. Розділ 81 — `pvgis_country_grid`, виявлено, що `CronJobRun.
   errorMessage` вже зберігався в БД, просто НІКОЛИ не показувався в
   UI — після цього фіксу подальші 500 стають самодіагностованими
4. Розділ 90 (суміжний клас) — `Article.status` ніколи не
   перераховувався при публікації перекладу — той самий "поле існує
   в схемі, але ніхто його не оновлює" патерн, інша область

**Урок**: коли backend повертає конверт-обгортку для debug-режиму,
КОЖЕН новий фронтенд-споживач цього ендпоінта ризикує повторити ту
саму помилку типізації, якщо не звірятись із РЕАЛЬНОЮ формою
відповіді щоразу. Розділ 76 — єдиний випадок, де підхід змінився з
реактивного (чекати скаргу) на проактивний (`grep` по всіх
admin-сторінках одразу після другого прояву) — це виявилось
ефективним, варто застосовувати systematic-перевірку одразу при
ПЕРШОМУУ прояві класу проблеми, не другому.

## Друга системна знахідка — `seed.ts` не був ідемпотентним (розділ 79)

`db-bootstrap.js` запускає `prisma db seed` на КОЖЕН старт
контейнера. Блок створення товарів не мав захисту від повторного
запуску — `product.create()` з унікальним `slug` падав на порушенні
унікальності при другому й наступних запусках. За цю фазу користувача
просили перезапускати контейнери десятки разів для застосування
різних фіксів — це означає, що ВСЕ, доданe в `seed.ts` ПІСЛЯ
товарного циклу (universal business-plan manifest, категорії
CABLE/CONNECTOR), могло НІКОЛИ реально не виконуватись на
живій БД користувача, залежно від того, коли саме стався перший
повторний запуск відносно порядку файлу. Виправлено перевіркою
`findFirst` ПЕРЕД створенням (потоварно, не блоком) — побічний ефект
на користь користувача: наступний реальний перезапуск коректно
ДОПОВНЮЄ вже частково заповнену БД, не потребує ручного очищення.

## Третя системна знахідка — Docker build "заморожував" сторінки (розділ 65)

Критична, знайдена без явної скарги користувача на цю конкретну
причину (користувач скаржився на симптом — "новостей так и нет").
`apiGet` під час збірки Docker-образу `web` намагається достукатись
до `api:3001`, якого на цьому етапі ще немає (окремі контейнери, `web`
збирається до старту `api`) — помилка мовчки проковтується `.catch()`,
Next.js трактує відсутність зовнішньої залежності як привід для
статичної генерації сторінки. Знайдено систематично (`grep -c apiGet`
по ВСІХ статично позначених маршрутах) — 6 сторінок з тим самим
патерном, найкритичніше — каталог товарів і `/financing` (щойно
збудований функціонал). Виправлено `force-dynamic` + `revalidate: 0`
на всіх 8 сторінках. Перевірка після фіксу зроблена НАПРЯМУ (файли
`.next/server/app/`), не на слово індикатора `●` у виводі збірки, який
виявився неточним для цього випадку.

## Честна епістемологічна історія — баланс акаунта Grok AI (розділи 80, 91-94)

Показова серія з чотирьох спроб, варта окремого відзначення для
майбутніх подібних задач:

1. Розділ 80 — перша спроба, шлях API вгаданий за аналогією, чесно
   позначено як здогадку
2. Розділ 91 — знайдено РЕАЛЬНИЙ баг у власній попередній реалізації
   (env-змінні не прописані в `docker-compose.yml` — значення в
   `.env` фізично не долітало до контейнера)
3. Розділ 92 — знайдено ТОЧНИЙ шлях через web_search (два незалежні
   джерела), число стало $27.23
4. Розділ 93 — виявлено розбіжність із реальним балансом ($9.19),
   спроба виправити самостійним підсумовуванням дала $157.23 —
   **гірше**, ніж попереднє наближення
5. Розділ 94 — після третьої невдалої спроби поспіль ЗУПИНЕНО, замість
   продовження гадання — замінено на пряме посилання на
   `console.x.ai`, джерело істини, яке намагались відтворити

**Урок**: коли послідовні спроби виправлення дають РІЗНІ, не
конвергентні результати (не наближення до істини, а віддалення) —
це сигнал зупинитись і запитати користувача про підхід, а не
продовжувати варіації на ту саму здогадку. Три невдалі спроби поспіль
— розумний поріг для цього.

## Великі функціональні доробки цієї фази

- **Кабелі та конектори** (розділ 77) — нова категорія каталогу з
  реальною формулою ΔU (перевірено web_search, не вигадано), три
  окремі кабельні задачі (DC-кабель, MC4-конектори по стрічках,
  AC-кабель зниження з прямим вводом відстані — єдина величина,
  фізично не визначана автоматично)
- **Мультикраїнність БД** (розділ 51) — `Country`-модель,
  `countryCode` на 6 таблицях, складені унікальні ключі, свідомо
  залишено поза обсягом Nova Poshta/повне узагальнення валюти
- **Тарифікація AI-витрат + вкладка "Витрати"** (розділи 78, 80) —
  обмежений scope (лише ітеративний квиз калькулятора, не парсери
  статей/фінансування), ціни підтверджені web_search
- **Статті — серія з ~10 взаємопов'язаних фіксів** (розділи 63, 67-76)
  — публікація/локалізація/скоринг/картинки/видалення, кульмінація —
  og:image fallback зі сторінки самої статті, коли RSS ГЕНУЇННО не
  несе картинку (не черговий здогад regex, а зміна підходу після
  підтвердження реальними логами)
- **Фінансові програми — дублікати та merge** (розділи 83-89) —
  евристика на основі домену URL/titleSimilarity, свідомо НЕ
  автоматичне рішення (можлива цінна деталізація, не завжди
  сміттєвий дублікат), сама можливість об'єднання, headless-браузер
  ескалація на 403/429
- **Перемикач стилів Classic/Modern** (розділи 95-96) — від
  компонентного підходу (не масштабується) до глобальних CSS-правил
  на основі реального inventory використовуваних класів (63 unique),
  точні токени з наданого користувачем ТЗ, свідоме обмеження обсягу
  (структурні вимоги ТЗ — sticky search, map/grid control — не
  реалізовані, це новий функціонал, не перефарбування)
- **Акордеон результатів калькулятора + адмінський перегляд** (розділ
  99) — 4 секції (квиз/специфікація/документація/експорт), READ-ONLY
  версія в адмінці

## Знайдені й виправлені власні помилки цієї фази (чесний перелік)

Ця фаза мала незвично багато випадків, коли власний код,
написаний раніше в ТІЙ САМІЙ фазі, виявлявся джерелом наступного бага
— підкреслює цінність систематичної перевірки, не лише "код
скомпілювався":

1. Розділ 84 — `findAllForAdmin(status)` для дублікатів фінансових
   програм: `published` рахувався фільтром вже відфільтрованого
   масиву, завжди повертав порожньо для вкладки DRAFT
2. Розділ 91 — `GROK_MANAGEMENT_API_KEY`/`GROK_TEAM_ID` додані в код,
   але забуто прописати в `docker-compose.yml`
3. Розділ 96 — при додаванні `text-sun-600` випадково повністю
   замінено сусідній рядок `bg-orange-50` замість додавання поряд —
   помічено й виправлено одразу повторною перевіркою
4. Розділ 99 — новий тип `generationStatus` спочатку мав неіснуючі
   значення (`GENERATING`/`READY`), перевірено напряму зі схеми,
   виправлено на реальні (`PROCESSING`/`COMPLETED`)
5. Розділ 78 — власна плутанина: побачив вивід `nest build` напряму
   (без стандартного відфільтрованого `tsc --noEmit`) і помилково
   повідомив про "реальну помилку" `UserRole`, що виявилась тим самим
   відомим шумовим артефактом пісочниці — виправлено повторною
   перевіркою стандартним способом

## Свідомі спрощення й обмеження обсягу, зафіксовані чесно протягом фази

- **Business Plan batch-обробка досі послідовна**, не паралельна —
  той самий, ще з Фази 4, незакритий пункт (мережа пісочниці не
  пускає на `api.x.ai` для перевірки batch/async-режиму)
- **PVGIS-карта потенціалу досі клієнтська теплова карта**, не
  PMTiles + серверна інтерполяція — той самий, ще з Фази 4, свідомий
  компроміс через відсутність GIS-тулінгу в середовищі
- **Windy — поточні умови вітру**, НЕ середньорічний потенціал для
  вітроенергетики (розділ 64) — чесно позначено як принципово інший
  показник, не видається за готовий інструмент вибору майданчика
- **Modern-тема — лише колірне покриття**, структурні вимоги наданого
  ТЗ (sticky search, map/grid control, camera-card-style компоненти)
  НЕ реалізовані — новий функціонал, не перефарбування (розділ 96)
- **`NOVA_POSHTA_API_URL` свідомо НЕ додано** в `docker-compose.yml`
  (розділ 91) — код вже має безпечний фолбек, додавання за тим самим
  патерном, що інші змінні, зламало б його (порожній рядок замість
  `undefined`, `??` на нього не спрацьовує)
- **`vendor.dto.ts`/`promo-settings.dto.ts`** — той самий жорсткий
  union тип категорій, що вже виправлявся в інших DTO (розділ 77),
  залишено як задел — опційні фільтри, не блокери

## Ще не закриті/невідомі причини (чесно, без вигаданих відповідей)

- Розділ 86 — нерегулярний 500 на `financing_program_parser` без
  збереженого `errorMessage`: гіпотеза про крах Node-процесу (OOM,
  headless Chromium під навантаженням) — захисні заходи вжиті
  (ресурсозберігаючі прапорці Chromium, timeout), але НЕ підтверджено
  напряму — `docker-compose.yml` явні memory limits свідомо не додані
  без знання реальних ресурсів хост-машини користувача
- Розділ 98 — 500 на `POST /calculator/start` з `AbortError` у
  логах: перевірено весь ланцюг викликів, необробленого винятку не
  знайдено — `AbortError`, ймовірно, стосується іншого запиту (наданий
  лог обрізаний). Додано видимість (try/catch на рівні контролера з
  реальним текстом помилки) замість подальшого здогаду — точна
  причина залишається невідомою до наступного реального прояву
