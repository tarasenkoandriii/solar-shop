# AUDIT-PHASE-3-DELIVERY.md — аудит фічі генерації та відправки матеріалів калькулятора

Дата: 17.08.2026. Скоуп — тільки `CalculatorService.exportPackage()`/`send()`,
`InvoiceService` (шаблон «Кошторис проєкту»), `EmailService`, розширення
`NotifyService.sendDocumentToUser()`, нова таблиця `ProjectEstimateDelivery`.
Решта калькулятора (квиз, резолвінг каталогу, `/account/projects`,
адмінка) — окремий `AUDIT-PHASE-3.md` (загальний).

## Знайдено й виправлено під час аудиту

### 1. Критично: відсутня перевірка власника розрахунку

До цієї правки жоден з ендпоінтів `refine`/`updateSpec`/`finalize`/
`addToCart`/`exportPackage`/`send`/`GET :id` не перевіряв, що виклик
дійсно робить власник `ProjectEstimate`. `estimateId` — `cuid()`, важко
підібрати брутфорсом, але міг **витекти** (referer, історія браузера,
випадковий шеринг посилання на «Кошторис готовий» — фічі публічного
шерингу в ТЗ немає, але сам факт, що id з'являється в URL фронтенду,
створює поверхню витоку).

**Найгірший сценарій**: зловмисник, який дізнався чужий `estimateId`, міг
викликати `POST /calculator/:id/send` з **власним** `contactValue` —
матеріали (специфікація, бюджет, місто) чужого проєкту пішли б на email/
Telegram зловмисника. Це не гіпотетична дірка в даних другорядної
важливості — це пряме витікання персональних даних клієнта через штатний,
задокументований ендпоінт.

**Виправлення**: доданий `CalculatorService.assertOwnership()` —
перевіряє `estimate.userId === поточний userId` (якщо є) або
`estimate.sessionId === переданий sessionId` (гостьовий сценарій), кидає
`ForbiddenException` інакше. Підключено до всіх 7 чутливих методів
(`findById`, `refine`, `updateSpec`, `finalize`, `addToCart`,
`exportPackage`, `send`). Контролер тепер приймає `sessionId` як query-
параметр на кожному з цих роутів (раніше приймав лише там, де він був
потрібен для самої бізнес-логіки, не для перевірки прав).

### 2. Реальний баг: `data:` URL PDF вставлявся як текст у тіло email

Коли `BLOB_READ_WRITE_TOKEN` не налаштований (типова ситуація в dev/
staging-оточенні без Vercel Blob), `InvoiceService.uploadToBlob()`
фолбечиться на `data:application/pdf;base64,...` замість реального
`https://` посилання — **свідоме** й задокументоване рішення ще з Фази 2
(«щоб функціональність не блокувалась повністю в dev»). Але
`EmailService` до цієї правки просто дописував будь-який
`attachmentUrl` як текст у тіло листа: `${text}\n\nPDF: ${attachmentUrl}`.

Для реального PDF у кілька сторінок це кілька мегабайтів base64-тексту
прямо в тілі листа — не рендериться як посилання, роздуває розмір листа,
частина SMTP-серверів ріже занадто довгі рядки/відхиляє лист цілком.

**Виправлення**: `EmailService` тепер розпізнає `data:` URL і прикріплює
його як справжнє MIME-вкладення (`attachments: [{filename, content:
base64}]`) — для Resend через їхній `attachments`-параметр API, для
SMTP-фолбеку через стандартний `nodemailer` `attachments`. Звичайний
`https://` URL (коли Blob налаштований) як і раніше йде текстовою
посилання — вкладення в такому разі не потрібне.

## Свідомі спрощення, які лишаються (не виправлено — задокументовано)

- **`WHATSAPP`/`VIBER` зі статусом `SENT` — умовний, не підтверджений**.
  Без платного Business API для обох каналів (WhatsApp Business API і
  Viber Business Messages — обидва вимагають реєстрації бізнес-акаунту,
  окремої верифікації, зайве для Фази 3, як прямо сказано в ТЗ п.31.6 щодо
  WhatsApp) відправка зводиться до діплінка з передзаповненим текстом
  (`wa.me`/`viber://forward`), який відкриває застосунок для **людини**,
  щоб натиснути «Надіслати» самостійно. Наш backend не отримує
  підтвердження, що повідомлення справді пішло — `SENT` означає лише
  «діплінк згенеровано і повернуто користувачу». Це чітко написано і в
  коментарях коду (`calculator.service.ts`), і в підказці на самій
  сторінці адмінки «Контакти доставки» — не прихована деталь.
- **Viber взагалі не було в оригінальному ТЗ** — доданий по окремому
  запиту, за тим самим паттерном компромісу, що й WhatsApp (діплінк
  замість Business API). На відміну від `wa.me`, у Viber немає
  універсального «відкрити чат із довільним номером і текстом» для
  контактів, яких ще немає в списку — використаний `viber://forward`
  (системний пікер «переслати» з передзаповненим текстом, отримувача
  людина обирає вручну). Це ще менш детерміновано, ніж `wa.me`.
- **Telegram-відправка мовчки провалиться без `BLOB_READ_WRITE_TOKEN`** —
  `NotifyService.sendDocumentToUser()` явно відмовляється відправляти
  `data:` URL (Telegram Bot API `sendDocument` очікує реальний `https://`
  URL або multipart-заливку файлу, не приймає `data:` URI) — **виправлення
  оминається**, повертає `false`, `CalculatorService.send()` ловить це як
  помилку і зберігає `ProjectEstimateDelivery.status = FAILED` з чітким
  `errorMessage`. Це коректна, зрозуміла поведінка, не тиха втрата даних
  — але означає, що в dev-оточенні без Blob канал Telegram для калькулятора
  просто не працюватиме, поки токен не буде додано.
- **`ProjectEstimateDiagram.svgUrl` для PRINCIPAL-схеми завжди `data:`
  URL**, на відміну від PDF (який намагається завантажити в Blob).
  Прийнятно — згенеровані SVG-схеми важать кілька кілобайт (прості
  блок-діаграми, не растрові зображення), зберігання в Postgres-полі
  `String` не є проблемою продуктивності на цьому обсязі. Якщо в
  майбутньому шаблони стануть значно складнішими/важчими — варто
  уніфікувати з PDF-плечем через Blob.
- **PDF «Кошторис проєкту» не вставляє сам SVG схеми як зображення** —
  `pdf-lib` не підтримує вбудовування довільного SVG напряму (тільки
  растрові PNG/JPEG або власне векторне малювання примітивами). PDF зараз
  містить лише текстовий опис (топологія, специфікація, анотація), не
  саму картинку схеми. Схема доступна користувачу окремо через
  `ProjectEstimateDiagram.svgUrl` на екрані результата, але **не всередині
  скачаного PDF-файлу** — це прямо суперечить буквальному ТЗ п.31.10.3
  («Итоговый PDF... многостраничный: спецификация → аннотация → блочная
  схема → принципиальная схема, одним файлом»). Чесно: це не реалізовано
  повністю, лише текстовий сурогат. Виправлення вимагає або растеризації
  SVG в PNG на бекенді (додаткова залежність типу `sharp`/`resvg`, яку не
  встиг підключити й перевірити в цій сесії), або переходу на інший
  PDF-генератор із підтримкою SVG.
- **Жоден мережевий виклик цієї фічі не протестований наживо** — Resend
  API, SMTP-сервер, Telegram `sendDocument`, Vercel Blob — мережа
  пісочниці, де писався код, не пускає на жоден із цих доменів. Логіка
  побудована за офіційною документацією кожного сервісу, але потребує
  перевірки на реальних credentials перед продакшеном.

## Рекомендовані наступні кроки

1. Растеризація SVG-схем у PNG для повноцінного вбудовування в PDF (закриває
   розбіжність із ТЗ п.31.10.3) — або зміна PDF-генератора.
2. Реальний прогін проти Resend/SMTP/Telegram/Blob із валідними ключами
   перед першим продакшн-релізом фічі.
3. Розглянути додавання `sessionId` у сам URL результату калькулятора
   (напр. підписаний токен замість голого `estimateId`) — додатковий шар
   захисту понад `assertOwnership()`, якщо посилання на результат колись
   почнуть шерити публічно (зараз не потрібно, `assertOwnership` вже
   закриває основний ризик).
