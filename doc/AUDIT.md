# AUDIT.md — аудит коду після реалізації Фази 1

Дата: 17.08.2026. Проведено відразу після написання коду, як і просив Andrii
(«провести аудит коду після написання»).

## Що перевірено

- `npm run build` для `apps/web`, `apps/admin`, `apps/tma` — **проходить
  чисто**, включно з type-checking (Next.js прогонює `tsc` як частину білда)
- `npx tsc --noEmit` для `apps/api` — **0 реальних помилок**; лишилось 14
  помилок, і всі 14 — виключно через відсутній згенерований Prisma Client
  (у sandbox-мережі, де писався код, заблокований `binaries.prisma.sh`; у
  звичайному оточенні `npm run db:generate` це закриває)
- Ручний прохід по маршрутизації API (порядок static/dynamic routes),
  cross-app контрактам (типи в `apps/web|admin|tma/lib/api.ts` звірені з
  Prisma-схемою та DTO), Dockerfile-ам, docker-compose

## Знайдені й виправлені під час аудиту

1. **Route collision у `ProductsController`**: `@Get('admin/all')` спочатку
   був оголошений після `@Get(':slug')` — Express перехопив би
   `/products/admin/all` як `slug='admin'` і повернув 404 замість списку для
   адмінки. Виправлено — статичні маршрути тепер оголошені раніше динамічних.
2. **CRUD виробників/офісів у адмінці не мав бекенду**: адмін-фронтенд
   спочатку викликав неіснуючі `POST /manufacturers`/`POST /offices`. Додав
   повноцінні admin-ендпоінти (`create`/`update`/`remove`, роль ADMIN) в
   `apps/api/src/manufacturers` та `apps/api/src/offices` — раніше в ТЗ явно
   вимагався CRUD цих сутностей у Фазі 1 (п.11), а не тільки товарів.
3. **Заявки (Lead) не мали зміни статусу з адмінки** — додав
   `PUT /leads/admin/:id/status` (ролі ADMIN/MANAGER) + фронтенд-селект
   статусу на сторінці `/leads`.
4. **`TelegramLoginDto` не сумісний із `TelegramAuthPayload`** — TypeScript
   помилка (`tsc --noEmit`) через відсутню індекс-сигнатуру, потрібну для
   динамічної побудови `checkString` при перевірці HMAC. Додав `[key: string]:
   unknown` до DTO.
5. **Мертвий код у `ProductsService.findAll`** — залишок раннього чернетки
   (`const specsFilters: Prisma.JsonFilter[] = []; ... void specsFilters;`),
   нічого не робив. Видалено, залишив коментар, чому три `if` на `where.specs`
   безпечні (тільки один ключ актуальний на категорію).
6. **Сміттєва помилка `sh`-скриптів**: кілька `mkdir -p .../{a,b,c}` не
   розгорнулись (пісочниця виконує `/bin/sh`, а не `bash`, brace expansion
   там не працює) — створювались директорії з буквальними фігурними
   дужками в імені. Знайшов і почистив усі випадки перед фінальною зборкою.
7. **`next@14.2.15` мав відому вразливість** (security advisory) — підняв
   до останньої патч-версії гілки `14.2.35` в усіх трьох Next.js застосунках.
8. **Дублікат `<html>/<body>`**: спочатку `app/[locale]/layout.tsx` (web)
   рендерив власні `<html>/<body>`, хоча кореневий `app/layout.tsx` теж мав
   їх — Next.js вимагає рівно один `<html>` на дерево. Переніс теги в
   кореневий layout, `[locale]`-layout тепер лише обгортка Header/Footer.
9. **Зайвий рядок у `apps/api/Dockerfile`**: `RUN npm install --workspaces=false
   || true` перед звичайним `npm install` — залишок чернетки, що нічого не
   давав (falsy-guard ловив будь-яку помилку). Прибрав.
10. **Serverless-запуск NestJS на Vercel Hobby не був реалізований** —
    спочатку `vercel.json` для `apps/api` вказував на `dist/main.js`, який
    викликає `app.listen()` і не працює як serverless-функція. Додав
    `apps/api/api/index.ts` — zero-config Node-функція з
    `@vendia/serverless-express`, що кешує Nest-застосунок між "теплими"
    інвокаціями (той самий підхід, що вже використовувався в Caller ID/BTW).
11. **Cross-domain cookie** (знайдено при першому аудиті, виправлено окремим
    заходом за проханням Andrii): `apps/web`/`apps/admin` тепер проксують
    `/api/*` на реальний `apps/api` через `next.config.mjs` rewrites
    (серверна змінна `API_INTERNAL_URL`), усі авторизовані браузерні запити
    (`TelegramLoginButton`, увесь `apps/admin/src/lib/api.ts`) переведені з
    прямих cross-origin викликів на `NEXT_PUBLIC_API_URL` на відносні
    `/api/...`. `Set-Cookie` від бекенду прозоро проходить через rewrite —
    браузер бачить його як first-party cookie домену web/admin,
    `sameSite: 'lax'` знову працює без переходу на `'none'`/`secure`.
    Публічні SSR-читання каталогу (`apiGet` у `apps/web/src/lib/api.ts`)
    навмисно лишені на прямому `NEXT_PUBLIC_API_URL` — це server-to-server
    виклик без cookie, проксі там не потрібне. Деталі — README п.4.3.
12. **Окремий бот для адмінки** (виправлено окремим заходом за проханням
    Andrii, одразу після п.11): офіційний Login Widget прив'язує домен до
    бота 1:1 через `@BotFather /setdomain`, тому `apps/web` і `apps/admin`
    на різних доменах не могли шарити одного бота — `apps/admin` формально
    показував би кнопку логіну, але підпис Telegram перевірявся б проти
    домену сайту й не проходив би для домену адмінки. Додав
    `TELEGRAM_ADMIN_BOT_TOKEN` (бекенд) + `NEXT_PUBLIC_TELEGRAM_ADMIN_BOT_USERNAME`
    (admin), новий ендпоінт `POST /auth/telegram/admin` (перевіряє підпис
    проти токена бота адмінки, `AuthService.loginWithTelegram(payload,
    'admin')`), `AuthGate.tsx` в admin оновлено під новий бот/ендпоінт.
    Модель `User`/ролі не змінились — розділені лише боти Login Widget, не
    дані. Деталі — README розділ 3 та п.4.4.

## Відомі обмеження й свідомі спрощення Фази 1 (не баги, а межі скоупу)

- **Vercel Cron не підключений** — курс НБУ (`syncFromNbu`) і зараз
  запускається лише вручну (кнопка адміна викликає `POST
  /currency/rate/sync`). Повноцінний суточний pg_cron-раннер — Фаза 2 (ТЗ
  п.16/27), у Фазі 1 явно позначено як не блокуючий реліз.
- **`Lead` замість `Cart`/`Order`**: продуктова сторінка веде на просту
  форму заявки (ім'я/телефон/коментар), а не в кошик — навмисно, кошик і
  чекаут — Фаза 2 за ТЗ. Модель `Lead` — свідомий тимчасовий місток, не з
  фінальної схеми з п.13.1.
- **Завантаження фото товару** — адмінка приймає URL-адреси рядками
  (textarea, по одному URL на рядок), а не файловий аплоадер у Vercel
  Blob/Supabase Storage. Повноцінний менеджер галереї з drag&drop — ТЗ
  п.26.4, заплановано доробити разом з парсером у Фазі 2, коли з'явиться
  реальна потреба масово вантажити фото.
- **`ProductForm` в адмінці** редагує specs/фото через сирий JSON/textarea,
  а не структуровану форму по категоріях (мощність для панелей окремим
  полем тощо) — свідоме спрощення для Фази 1, специфікація полів різна на
  категорію і структурована форма додає суттєвий обсяг коду без якого
  каталог все одно повністю функціональний.
- **Без Sentry/аналітики** (ТЗ п.30.1) — прямо вказано в ТЗ як «не блокер
  першого релізу».
- **`prisma generate`/повний білд `apps/api` не перевірені наживо в цій
  сесії** — мережевий allowlist пісочниці, де писався код, не включає
  `binaries.prisma.sh` (Prisma качає бінарники engine з окремого CDN). Це
  обмеження середовища розробки коду, а не самого коду: команда стандартна
  і відпрацює на звичайній машині/CI/Vercel. Рекомендую перед деплоєм
  прогнати `npm run db:generate && npm run build --workspace=apps/api`
  локально одразу після клонування, щоб зловити типізаційні помилки (якщо
  такі є) до пушу.

## Рекомендовані наступні кроки (не Фаза 1, але варто мати на увазі)

1. Виправити cross-domain cookie (п. вище) — це реально заблокує Login
   Widget на проді, якщо не поправити перед першим деплоєм.
2. Додати `ESLint`/`Prettier` конфіги в корінь монорепо — зараз їх немає,
   білд Next.js ловить лише type-errors через вбудований `tsc`-крок, а не
   стиль/потенційні багі рівня ESLint-правил.
3. Розглянути `packages/shared` (вже створений як порожня заготовка) для
   спільного `slugify()`/`articleNumber` генератора — зараз ця логіка
   продубльована в `packages/db/prisma/seed.ts` і
   `apps/api/src/products/products.service.ts`.
