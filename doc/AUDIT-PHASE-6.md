## Що перевірено

Не лише переказано зміст README — цілеспрямовано перевірено НАПРЯМУ
в поточному коді (не на слово попередніх записів):

- `npx tsc --noEmit` для `apps/api` — 0 реальних помилок на момент
  написання аудиту
- Баланс `{`/`}` у `schema.prisma` — 78/78, збіг (файл пройшов через
  чотири окремі редагування за цю фазу, включно з одним, що ламало
  структуру, розділ нижче)
- `pickWithReliability()` (калькулятор) звертається ЛИШЕ до
  `productReview` (verified purchase), НІ РАЗУ до
  `importedProductReview` — підтверджує заявлене в розділі 103
  ("свідомо НЕ підключено") реальним переглядом коду, не на довіру
  власному попередньому запису

## Найважливіша знахідка цього аудиту — делегації "зникають" після створення

`ProfitService.delegateNoProfitOrders()` (розділ 104) створює
`OrderDelegation` записи з `ttnNumber`/`ttnRef`/`ttnStatus` — АЛЕ:

- **Немає жодного `GET`-ендпоінта** для читання `OrderDelegation` —
  перевірено `grep` по `orders.controller.ts`/`orders.service.ts`, 0
  збігів
- Детальна сторінка замовлення в адмінці (`/orders/[id]`) **нічого не
  знає** про делегації — 0 згадок, перевірено напряму
- `OrderDelegation.ttnLabelUrl` оголошено в схемі, але НІКОЛИ не
  заповнюється (на відміну від `Order.ttnLabelUrl`, який реально
  оновлюється в `printLabel()`) — немає способу роздрукувати етикетку
  делегованого відправлення взагалі

**Практичний наслідок**: після натискання "Делегувати замовлення" на
сторінці Profit менеджер бачить лише АГРЕГОВАНУ статистику
("делеговано N позицій, створено M груп, ТТН створено K") у
модальному результаті одразу після дії — і БІЛЬШЕ НІКОЛИ не може
побачити ці дані знову: який конкретно постачальник отримав які
товари, який номер ТТН у кожної делегації, чи потрібно щось
роздрукувати для відправки. Дані РЕАЛЬНО зберігаються в БД (сама
модель і створення записів коректні), просто не мають жодного шляху
перегляду після миттєвого результату дії. Це не було зазначено як
свідоме обмеження в розділі 104 — там описано архітектурне обмеження
Nova Poshta Sender Ref (чесно), але не цей окремий, суто UI-шний
пробіл. Виправлення: новий `GET /admin/orders-profit/delegations`
(або розширення `/orders/:id` відповіддю з `delegations`) +
відображення на сторінці замовлення чи окремою секцією на Profit —
не зроблено в межах цієї фази, потребує окремого проходу.

## Другий системний урок — той самий клас "власна робота ламає власну ж роботу", що вже в Фазі 5

Ця фаза мала ДВА окремих випадки пошкодження файлу редагуванням
власного коду ТІЄЇ Ж фази (не спадок попередніх фаз):

1. Розділ 103 — `str_replace` при додаванні `ImportedProductReview`
   частково стер `ProductImage` (замінив початок моделі, лишив хвіст
   без нього). Знайдено й виправлено ОДРАЗУ повторною перевіркою
   результату редагування — не на наступному кроці, не користувачем.
2. Розділ 104 — `byVendor.get(vendorId) ?? { vendorId, itemIds: [] }`
   — TypeScript не зміг вивести тип порожнього масиву з контексту `??`
   (реальна помилка компіляції). Знайдено цілеспрямованою перевіркою
   компілятора одразу після написання, не залишено до випадкового
   виявлення пізніше.

**Урок, що повторюється з Фази 5**: після КОЖНОГО редагування
багаторядкових Prisma-моделей чи складних generic-конструкцій —
перевірка результату ОДРАЗУ (не "на слово" успішного `str_replace`)
залишається необхідною практикою, не одноразовою рекомендацією.
Обидва випадки цієї фази БУЛИ спіймані вчасно — практика працює, але
сам факт повторення класу помилки (тепер третій-четвертий раз за дві
фази поспіль) вартий явної згадки.

## Ланцюг взаємопов'язаних рішень — перевірено на несуперечність

Розділи 101→102→103→104 — не незалежні фічі, а послідовні уточнення
однієї теми. Перевірено, що пізніші розділи НЕ суперечать раніше
заявленим принципам:

- Розділ 101 заявляє "verified purchase, не Telegram-логін" →
  розділ 102 ПОСИЛЮЄ це (прив'язка до конкретного `OrderItem`, не
  просто "якесь замовлення товару") — узгоджено, не ослаблено
- Розділ 101 заявляє "рекомендації НЕ враховуються для імпортованих
  відгуків" → розділ 103 (новий тип відгуків) підтверджує це
  структурно (`ImportedProductReview` — окрема модель, `groupBy`
  калькулятора звертається лише до `productReview`) — перевірено
  напряму в цьому аудиті, не на слово
- Розділ 104 (ціна) НЕ змінює семантику `cachedPriceUsd` для
  споживачів цього поля (каталог/калькулятор) — підтверджено: жодних
  правок у `apps/web` за розділ 104, лише `computeProductPricing()` і
  місця збереження результату

## Свідомі обмеження, вже чесно зафіксовані в самих розділах (не повторюю тут детально)

- Розділ 103: селектори 3 з 4 review-адаптерів не перевірені проти
  живого DOM (лише sunshop.com.ua підтверджено прямим `web_fetch`)
- Розділ 104: делегування — НЕ справжній drop-shipping (немає Nova
  Poshta Sender Ref для Vendor), фізичний відправник лишається наш
- Розділ 101: рекомендації враховуються лише для батареї/контролера,
  не панелей/кабелю/конекторів (структурне обмеження вибору "з
  відкритого переліку кандидатів")
