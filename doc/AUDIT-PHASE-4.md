## Найважливіше свідоме спрощення — карта потенціалу

ТЗ п.34.2 описує повний конвеєр: офлайн-сітка точок PVGIS → геопросторова
IDW/кригінг-інтерполяція → растр → **PMTiles** → рендер через Leaflet/
Mapbox GL/deck.gl із кольоровим градієнтом.

**Що реалізовано насправді**: офлайн-прогін сітки точок через PVGIS —
реальний і робочий (`SolarMapService.recomputeGrid()`, розширює вже
спроєктовану `SolarYieldEstimate` з точки на країну, як і задумано ТЗ, без
нової моделі). Але замість PMTiles + серверної інтерполяції — сирі точки
сітки віддаються клієнту напряму, рендер через `leaflet.heat`
(клієнтська теплова карта по точках, без інтерполяції між ними на
сервері).

**Чому**: побудова реального PMTiles-пайплайна вимагає GIS-тулінгу рівня
`tippecanoe`/GDAL — цих інструментів немає в середовищі, де писався код, і
їх не можна було б надійно перевірити без мережевого доступу для
встановлення/збірки. `leaflet.heat` — це все ще теплова карта (не анімація
частинками, як прямо вимагає ТЗ — цей принцип дотримано), просто без
геопросторової інтерполяції та тайлування. При **грубій сітці** (крок 1°,
тобто ~111 км) точок мало і клієнтська теплова карта виглядатиме
"плямами", а не гладким градієнтом — на відміну від справжньої
IDW/кригінг-інтерполяції. Якщо крок сітки зменшити (детальніша),
`leaflet.heat` виглядатиме прийнятніше, але кожен додатковий градус
сітки — це квадратично більше викликів PVGIS при перерахунку.

**Наслідок для продакшену**: перш ніж вважати карту готовою, варто або (а)
зменшити крок сітки й прийняти клієнтську теплову карту як остаточне
рішення, або (б) окремим проєктом побудувати реальний
інтерполяція+PMTiles конвеєр (Python-скрипт з `scipy`/`pykrige` +
`tippecanoe`, що генерує статичні тайли одноразово — не частина
NestJS-бекенду).

## Знайдено й виправлено під час написання коду

1. **Пошкоджена сигнатура методу в `GrokService`** — під час вставки нових
   методів Фази 4 випадково обрізав закриваючу дужку існуючого
   `chatJson()`, через що файл втратив коректну структуру. Знайдено
   одразу через `tsc --noEmit` (перевірка типів після кожного великого
   блоку правок — та сама дисципліна, що застосовувалась у всіх
   попередніх фазах), виправлено до продовження роботи.
2. **Копіпаст-баг у `fillBusinessPlanContent`** — у чернетці методу
   помилково передав `input.manifestContent ? input.projectSummary : ''`
   замість реального промпту з обома полями — весь контент маніфесту
   губився б. Виправлено до комміту (той самий прохід tsc допоміг
   виявити структурну проблему, сам логічний баг усвідомлено
   переглянутий і виправлений вручну при рев'ю коду).

## Свідомі спрощення, зафіксовані чесно

- **`business_plan_batch_processor` виконує виклики Grok послідовно, не
  паралельно й не через окремий batch/async-режим Grok API**. ТЗ п.31.11.0
  прямо каже: "якщо у Grok API виявиться окремий batch/async-режим із
  нижчою ціною — використати його, перевірити на етапі імплементації".
  Перевірити це в цій сесії не було можливості (мережа пісочниці не
  пускає на `api.x.ai`) — залишено як послідовні виклики, чесно
  задокументовано в коді сервісу як пункт для подальшої перевірки.
- **PDF «Бізнес-план» без пагінації на кілька сторінок** — якщо
  згенерований Grok-ом текст довший за одну A4-сторінку, зайвий текст
  просто обрізається (`if (y < 60) return`) замість переносу на нову
  сторінку. Той самий компроміс, що вже був у PDF кошторису проєкту
  (Фаза 3) — `pdf-lib` без обгортки для автоматичної розбивки на
  сторінки, вартий доопрацювання перед реальним використанням для
  великих документів.
- **Логіка `IDENTICAL_SEGMENTS` у `planPhases()` спрощена до тієї самої
  формули, що й `HEADROOM`** — реальна відмінність між двома стратегіями
  (сегменти повинні бути ідентичними модулями, що можна докуповувати
  незалежно, тоді як HEADROOM бере контролер одразу повного розміру) не
  розрізняється в коді розбиття на етапи — обидві стратегії масштабують
  панелі/АКБ пропорційно бюджету, різниця тільки в тексті опису. Чесна
  MVP-версія, не повна реалізація різниці між двома стратегіями з
  ТЗ п.31.12.1.
- **`FinancingService.runParser()` дедуплікація по `name`+`url` крихка**
  — якщо Grok поверне трохи іншу назву тієї самої програми (напр.
  "Ощадбанк Енергонезалежність" замість "Ощадбанк — «Енергонезалежність»")
  при повторному прогоні, дублікат не буде відфільтрований точним
  збігом рядка. Для MVP прийнятно (модерація адміном все одно потрібна
  перед публікацією), але вартий кандидат на fuzzy-порівняння назв у
  майбутньому.
- **`/embed/solar-map` параметри `?city=`/`?region=` приймаються, але не
  впливають на дані** — сітка PVGIS єдина для всієї України, регіональне
  фокусування (щоб стороннє СМІ показувало карту свого регіону) не
  реалізовано, тільки задокументовано як TODO в коментарі до сторінки.
- **Жоден реальний зовнішній виклик не протестований наживо** — та сама
  причина, що й у попередніх фазах: мережа пісочниці не пускає на
  `api.x.ai` (Grok з веб-пошуком для `FinancingService.runParser()`),
  `re.jrc.ec.europa.eu` (PVGIS для сітки карти).

## Рекомендовані наступні кроки

1. Реальний прогін `financing_program_parser` з валідним `GROK_API_KEY` —
   перевірити якість веб-пошуку Grok і формат знайдених даних відповідає
   очікуваному.
2. Розглянути окремий офлайн-пайплайн (не частина NestJS API) для
   реальної PMTiles-генерації карти потенціалу, якщо клієнтська теплова
   карта виявиться візуально недостатньою.
3. Доопрацювати `planPhases()` для реальної різниці між HEADROOM та
   IDENTICAL_SEGMENTS (наразі — та сама формула з різним текстовим
   описом).
4. Додати пагінацію на кілька сторінок у PDF-генераторах (кошторис +
   бізнес-план) — зараз текст обрізається, якщо не влазить на одну A4.
